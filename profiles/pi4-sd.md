# Raspberry Pi 4 on a single SD card

Pi 4 bootstrap images import the [SD-card profile](sd-card.nix). Import it in the permanent machine configuration to keep volatile journals, tmpfs, zram, disabled core dumps, disabled Tailscale diagnostic logging and disabled scheduled store optimisation across `nh` deployments. Measure remaining writes on the card under the intended workload. For a Pi where a failed update would require a site visit, the read-only A/B layout below is a separate bench trial.

## What the current configuration does

The [flake](../flake.nix) exposes a Pi 4 bootstrap image using U-Boot. It has no installed Pi 4 host definition. The [installed Pi 5](../machines/rpi5.ldn/default.nix) is a development and inference machine. Its Wi-Fi and firmware mount are relevant precedents. Its workload is a poor baseline for measuring an idle Pi 4.

| Source of writes                | Current behavior                                                                                                                                                                              | Proposed installed profile                                                                                                                                                                                                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Use ext4 with `noatime` for writable state. Keep journaling and normal write barriers for power-loss recovery. Keep the real firmware filesystem mounted during bootloader updates and verify the new generation after reboot. On Pi 5, an unmounted firmware partition previously let updates write to a shadow directory on root. Independently validate the Pi 4 boot path. [Raspberry Pi filesystem resilience guide](https://pip-assets.raspberrypi.com/categories/685-app-notes-guides-whitepapers/documents/RP-003610-WP-3-Making%20a%20more%20resilient%20file%20system.pdf)

## State that must survive power loss

- Persist the root-only Tailscale state directory, machine ID, SSH host keys and the host's ragenix decryption identity. Persist the uplink configuration, including encrypted Wi-Fi credentials if needed. DNS, usable time and a working uplink must be available before Tailscale can rejoin. The common network module disables DHCP by default. Explicitly configure wired or wireless addressing in the installed host. [Network defaults](../common/network.nix) · [Pi Wi-Fi precedent](../machines/rpi5.ldn/default.nix)
- Preserve the system random seed and a clock floor on a Pi without a battery-backed RTC. Keep required application data and any updater state. Mount persistent state before its consumers start. A failed mount should produce a visible failure before a service generates a replacement identity.
- For normal Nix deployments, retain the Nix store, database, generation links and matching boot files. Back up irreplaceable state to an encrypted off-device destination. Restore a Tailscale identity only when its previous instance is retired. Monitor a real SSH connection and the workload from another node.

## Three storage layouts

| Layout                                                                 | Steady state                                                                                                       | Upgrade and recovery                                                                                                                                           |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writable ext4 with the low-write settings above                        | Smallest change. New services can still introduce writes.                                                          | Existing fleet `nh` workflow. Retained generations support rollback when an operator can reach the machine or boot menu.                                       |
| RAM root with persistent `/nix` and explicit state                     | Disposable paths disappear on reboot. RAM needs a budget. Missing a persistence rule can break the next cold boot. | Retains `nh`. Store, boot and state still receive writes. Automatic fallback needs separate boot integration.                                                  |
| Read-only boot and OS slots A/B, shared state, RAM for transient paths | SquashFS or EROFS prevents incidental writes to the active OS.                                                     | Build releases off-device, write the inactive slot, trial-boot once and promote only after a health check. Requires space for both slots and an image updater. |

For a remote appliance, trial **Raspberry Pi firmware `tryboot`** on the actual board revision and EEPROM. Pi 4B revisions 1.0 and 1.1 require writable EEPROM for this feature. Give each release both its kernel/firmware boot files and matching root. Keep a separate journaled state partition. Mount active OS and boot files read-only during normal operation. A one-shot trial reverts on reset until explicitly promoted. A watchdog must cause that reset when a trial hangs. Bound connectivity checks so an external outage can fall back once without creating a reboot loop. Both slots must be able to read shared state after an upgrade. [Pi A/B boot selection](https://www.raspberrypi.com/documentation/computers/config_txt.html#autoboottxt)

Rugix is a candidate for this trial. It exports a NixOS module and a bundle builder, with a Pi `tryboot` backend. Board layout, update signing, boot integration and health-gated promotion still need validation. RAUC is an alternative for the current U-Boot route, with a boot-selection script and persistent U-Boot environment. NixOS also ships an image-based appliance profile and repart tooling. That profile disables Nix and system switching. An image-updated appliance therefore needs an explicit exception to the fleet's `nh` deployment convention before adoption. [Rugix Nix integration](https://github.com/rugix/rugix/blob/main/CHANGELOG.md) · [Rugix boot flows](https://github.com/rugix/rugix/blob/main/crates/apps/rugix-ctrl/schemas/system.sidex) · [RAUC U-Boot integration](https://rauc.readthedocs.io/en/latest/integration.html#u-boot) · [Pinned NixOS appliance profile](https://github.com/NixOS/nixpkgs/blob/f68407657ad294471eb4b2e65d193df26edf729f/nixos/modules/profiles/image-based-appliance.nix)

## Bench acceptance before remote placement

1. Identify the card with `lsblk`. From another host, sample `awk '{print $5, $7}' /sys/block/mmcblk0/stat` twice in the same boot. Subtract the readings. Field 5 counts completed writes. Field 7 counts 512-byte sectors written. Record an idle day, representative workload, boot and update separately. Capture measurements off-device. For A/B, check individual partition counters too. Require zero writes to active boot and OS partitions during steady state. Block counters measure host writes; SD controller wear amplification is invisible. [Linux block statistics](https://docs.kernel.org/block/stat.html)
2. On a bench unit, record the running generation, SSH fingerprint and Tailscale `.Self.ID`. Cut power, boot with the uplink unavailable, then restore connectivity. Verify a new SSH session from an authorized peer, the same identity, a successful scrape and the expected workload. Repeat without the first-boot key.
3. On A/B, interrupt an inactive-slot update. Then exercise two bad trials: a kernel that fails to boot, and a system that boots with broken networking. In both cases require the previous slot to come back remotely without human intervention. Also interrupt promotion to exercise the shared boot selector. A successful trial must serve the workload and prove inbound management reachability before promotion. Reboot again and confirm promotion persisted.
4. Compare idle and update bytes across the candidate layouts before choosing one. Confirm headroom for a complete update, memory pressure, and recovery of application data. Both slots share a single physical card. Recovery from total card failure requires replacement media or an independent boot path.
